## Existing pipeline

`ExifParser` uses `ExifReader.load(..., { includeUnknown: true })`, flattens each tag to its `value`, selects the first matching metadata processor, validates the result with `imageMetaSchema`, and sends that metadata through `addPostImage`.

Parser order is `automatic`, `swarmui`, `rfooocus`, `comfy`. MetaHub Save Node PNGs contain an A1111-compatible `parameters` chunk with `Steps:` plus standard ComfyUI `prompt` and `workflow` chunks. Consequently, `automatic` is selected before `comfy`.

Before this change, the Save Node wrote:

- `parameters` as PNG `tEXt`, built by `build_a1111_metadata`;
- `imagemetahub_data` as PNG `iTXt` JSON;
- `workflow` as PNG `tEXt` JSON;
- `prompt` as PNG `tEXt` JSON.

The workflow and prompt payloads are preserved and the active save node is rewritten from `SaveImage` to the matching MetaHub node class before serialization.

## Metadata contract

New outputs expose two generic metadata fields: PNG uses `tEXt` chunks, while JPEG and WebP use XMP properties:

```text
engine = ComfyUI
tools = ["Image MetaHub"]
```

`tools` is a JSON array, not a delimiter-based string. This keeps engine attribution semantically distinct from additional creation, processing, editing, or saving tools. The fields survive `ExifReader` independently of which generation parser wins.

The same values are included in `imagemetahub_data` for MetaHub consumers, while the separate PNG/XMP fields are the upstream interchange contract. Existing `parameters`, `workflow`, `prompt`, and `imagemetahub_data` fields are unchanged.

## Upstream behavior

The parser layer merges a valid explicit `engine` chunk and JSON `tools` chunk into parsed metadata after the selected generation parser runs. The image schema normalizes tool declarations before ingestion.

Limits for untrusted upload metadata:

- at most 10 declarations are considered;
- names are trimmed, non-empty, and at most 80 characters;
- the raw JSON declaration is capped at 2,048 characters before parsing;
- non-string entries, invalid JSON, and duplicate names are discarded;
- names resolve only against existing Tool aliases/names;
- additional names use one bounded database query;
- unknown tools are ignored and lookup failure does not fail the upload.

Primary attribution preserves existing behavior: `engine` remains preferred, and `external.source` remains the fallback only when engine is absent. Additional tools are additive to either path and the resulting IDs are deduplicated.

## Upstream PR copy

Title:

```text
Support additional tools declared by image metadata
```

Body:

```markdown
## Summary

Allow image metadata to declare additional tools involved in producing or processing an image while preserving the existing generation-engine attribution.

Generation pipelines can involve more than one tool:

`generation engine → saver → editor → post-processor`

The current automatic attribution path resolves essentially one Tool from `engine` (or the existing external-source fallback). This change accepts a bounded `tools` array from metadata, resolves existing Tool aliases/names in one query, and adds the matching IDs without replacing the primary Tool.

## Safety and compatibility

- Does not create Tool records from metadata.
- Ignores unknown, malformed, empty, or oversized declarations.
- Limits declarations to 10 names of at most 80 characters.
- Deduplicates IDs across primary and additional attribution.
- Keeps existing uploads unchanged when `tools` is absent.
- Keeps additional-tool lookup failures non-fatal.

## Tests

- Generic alias/name resolution and additive association tests.
- Unknown, duplicate, malformed, oversized, external-source, and absent metadata cases.
- End-to-end PNG fixture coverage through ExifReader, metadata parsing, schema validation, and tool-ID resolution.
```
